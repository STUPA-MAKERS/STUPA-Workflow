# Audit Log — `backend/app/modules/audit`

**Does:** Append-only, tamper-evident audit log. The service hashes every security, config, or money relevant action into a forward-linked chain (`hash = sha256(prev_hash || canonical_json(entry))`). The verify route re-checks that chain end to end. Other modules write entries through a service hook. Admins read, verify, and revert config/budget changes from the log.

**Key files:**
- `service.py` — `AuditService` (record/verify_chain/verify_and_store/run_manual_verification/prune_verifications/latest_verification/query/query_cursor/list_actors + actor/target/data-id resolvers) and the module-level `record()` hook that other modules call.
- `models.py` — `AuditEntry` ORM row (`audit_entry` table). Append-only: a DB trigger and the least-privilege `audit_writer` grant block UPDATE and DELETE (both in the baseline migration). `AuditVerification` (`audit_verification` table, Z6/O8) holds the stored chain checks. It is NOT part of the chain and NOT append-only.
- `worker/audit_verify.py` — the nightly cron `process_audit_verification` (04:30) and `verify_after_restore`, which `worker/backup.restore_backup` calls.
- `hashing.py` — pure `canonical_payload(...)` (deterministic UTF-8 bytes, UTC-normalized `at`, sorted keys) and `compute_hash(prev_hash, canonical)`.
- `actions.py` — `AuditAction` StrEnum (closed action catalog) + `REVERTABLE_BUDGET_ACTIONS` frozenset.
- `router.py` — `/admin/audit` FastAPI router (list/actors/verify/revert).
- `schemas.py` — read-only camelCase out-models (`AuditEntryOut`, `AuditPageOut`, `AuditActorOut`, `ChainVerificationOut`, `AuditVerificationOut`, `AuditRevertOut`).
- `__init__.py` — re-exports `AuditAction`, `AuditService`, `record`.

**Domain / data model:**
- Table `audit_entry`: `id bigserial` PK (generation order = chain order), `actor` (Principal `sub`, nullable = system/anon), `action` (text, from `AuditAction`), `target_type`/`target_id` (nullable), `at` (tz-aware, `now()` default), `data` JSONB (`{}` default, **id-references/metadata only, never raw PII**), `prev_hash` bytea (nullable, genesis links from `b""`), `hash` bytea. Indexes: `ix_audit_entry_at`, `ix_audit_entry_target_type_target_id`.
- `AuditAction` catalog: `login`, `status_change`, `vote_cast`, vote lifecycle (`vote_open`, `vote_close` with the result and the counts, `vote_cancel` with the reason, `vote_branch_blocked`, `vote_delete`; F12, never a voter), `application_create_on_behalf` (#11: the capturing person as actor; `applicantKind`, `applicantPrincipalId`, `receivedOn`, `intake` as a flag, never PII), `config_change`, `config_activation`, `config_revert`, `role_change`, `delegation_grant/revoke/use/substitute_add/substitute_remove`, `export`, meeting and agenda (F12: `meeting_create`, `meeting_update`, `meeting_delete`, `agenda_item_add`, `agenda_item_update`, `agenda_item_remove`, `agenda_reorder`, with id references and planning values only, never the Markdown text), attendance by the meeting lead (`attendance_set`, `attendance_reset`; Z2/F12, the status before and after, never the note), `protokollant_handover` (Z3: `mode` now/next_item/activate/cancel, the principal ids `from` and `to`, the current agenda item), `protocol_finalize` (F8/F12: the start of a finalization, with the meeting and the gremium), `webhook_config`, `attachment_upload/quarantine/delete` (F12; a draft of the wizard carries `draft: true` instead of `application_id`, Z4), PII/DSGVO (`pii_access/deletion/export`, `anonymization`, `erasure_requested/executed/rejected`, `principal_erased`, `retention_anonymize`), budget (`budget_node_create/update/delete`, `budget_allocation_set`, `budget_expense_create/update/delete`, `budget_transfer_create`, `budget_invoice_create/update/delete`, `budget_assign`, `budget_move_fiscal_year`).
- `REVERTABLE_BUDGET_ACTIONS` = node_create/update, allocation_set, transfer_create, expense_create/update. Deletes and assign/move are NOT revertable on purpose (see [[revert-feature-scope]]).
- Chain verification (`ChainVerification` dataclass): catches `hash_mismatch` (mutated field) and `prev_hash_mismatch` (removed/inserted row). It reports the first `broken_at` id (fail-closed).
- Table `audit_verification` (migration `373c9fe9cafb`): `id` uuid, `started_at`, `finished_at`, `valid`, `checked`, `broken_at` (the first broken `audit_entry.id`, **no FK** on purpose), `reason`, `trigger`, `triggered_by` (principal `sub`; NULL for the cron). CHECKs: `trigger IN (cron, manual, restore)`, `reason IN (prev_hash_mismatch, hash_mismatch)` or NULL, and `valid = (reason IS NULL)`. Index `ix_audit_verification_started_at` on `started_at DESC`. `VERIFICATION_KEEP = 100`, `MANUAL_VERIFICATION_COOLDOWN = 5 min`.

**API surface** (mounted under `/api`, prefix `/admin/audit`):
- `GET /api/admin/audit` — P(`audit.read`). Keyset-paged log (`before` cursor, newest first) with the filters `action`/`actor`/`since`/`until`. It resolves actor names, target labels, and embedded `data` UUIDs to clear names. Returns `AuditPageOut` (`items`, `nextCursor`, `hasMore`).
- `GET /api/admin/audit/actors` — P(`audit.read`). Distinct actors with resolved names (actor-filter dropdown).
- `GET /api/admin/audit/verify` — P(`audit.verify`). It recomputes the whole chain live, stores nothing and returns `ChainVerificationOut`. The MCP tool `verify_audit_chain` uses it.
- `POST /api/admin/audit/verify` — P(`audit.verify`). It recomputes the whole chain, stores the result with `trigger = manual` and `triggeredBy = sub`, and returns `AuditVerificationOut`. It gives 409 (`audit_verify_running`) while another check holds the check lock, and 429 (`audit_verify_cooldown`, with `Retry-After`) when a manual check started less than 5 minutes ago.
- `GET /api/admin/audit/verify/latest` — P(`audit.read`). The newest stored check (`AuditVerificationOut`), or `null` before the first one. It feeds the admin tile "Audit-Kette intakt" and the MCP tool `get_latest_audit_verification`, without the cost of a full check.
- `POST /api/admin/audit/{entry_id}/revert` — P(`audit.revert`). It undoes the config/budget change of the entry through `config_revision.RevertService`. It returns 404 when the entry or the revision is missing, and 409 when the change is not revertable or is stale. The revert is itself logged and revertable.

**Conventions & gotchas:**
- **Write through the hook, never raw-insert:** `await record(session, actor=..., action=..., target_type=..., target_id=..., data=...)`. It does NOT commit. It runs in the caller's transaction, so the audit row is atomic with the audited change. `data` MUST hold only id-references and metadata, never raw PII. That is the caller's responsibility.
- **Append serialization:** `record()` takes a fixed transaction advisory lock (`pg_advisory_xact_lock`, key `0x415544495400`) before it reads the previous `hash`. Concurrent appends therefore cannot race on `prev_hash`. Do not bypass the lock.
- **Hash determinism:** `canonical_payload` sorts the keys, uses compact separators, and normalizes `at` to UTC ISO-8601 (a naive value counts as UTC). The digest is therefore reproducible for any key insertion order and any server timezone. Non-JSON-native values in `data` raise `TypeError` on purpose (fail-closed). Any change to the canonicalization breaks verification of the existing rows.
- **No mutation path:** the ORM has no update or delete for `AuditEntry`. The DB enforces append-only with a trigger and the `audit_writer` least-privilege grant (defined in the baseline migration). Do not add an UPDATE or DELETE statement.
- **`verify_chain` streams** rows through a server-side cursor (`stream_scalars`). Very long logs stay verifiable because the whole chain never enters memory. It reads with `populate_existing`, so a row that the session identity map still caches cannot hide a change in the database.
- **Stored checks (Z6/O8):** `verify_and_store(trigger=..., triggered_by=...)` runs `verify_chain`, inserts one `audit_verification` row, prunes (`prune_verifications`) and **commits**. The prune keeps the newest 100 rows (order `started_at DESC, id DESC`) and, past them, the **first failed check of each break** (the oldest row of each distinct `(broken_at, reason)`, via `DISTINCT ON`) and the **newest check of each trigger**. Thus a series of manual checks cannot push the first detection of a break out of the store. The later failed checks of the same break are repeats, and the prune deletes them like valid rows. `audit_entry` is append-only, so a break stays until a restore and every later check fails. Without this rule the table would grow by one row per check. Each check holds a transaction advisory lock (`_VERIFY_LOCK_KEY`): the cron and the restore wait for it, `run_manual_verification` (the `POST /verify` path) only tries it and refuses with 409, then refuses with 429 inside the manual cooldown. It logs the duration (`duration_ms`) on the `app.audit` logger, at ERROR for a broken chain. Three triggers write rows: the worker cron at 04:30 (`trigger = cron`, independent of the 04:00 backup, so it also runs when backups are off or failed), `restore_backup` right after the restore audit entry (`trigger = restore`, in the restored database; a failure there only logs and never fails the restore, for example an archive without the table), and `POST /verify` (`trigger = manual`).
- **Three separate permissions:** `audit.read` (read/list/actors, and the stored latest check), `audit.verify` (run a chain check, live or stored), and `audit.revert` (destructive undo). Keep them distinct. RBAC is fail-closed (401 without a session, 403 without the permission).
- **No UUIDs in UI** ([[no-uuids-in-ui]]): the router batch-resolves the actor `sub`, `(target_type,target_id)`, and every UUID-shaped value inside `data` to clear names on the server. It calls `resolve_actor_names`/`resolve_target_labels`/`resolve_data_ids` (i18n labels prefer `de`). Resolution is best-effort. Deleted or unknown ids fall back to the raw value in the FE. A new `target_type` or `data` entity ref needs an extension of these resolvers.
- `query_cursor` reads `limit+1` to compute `has_more` without a COUNT, which scales on long logs. The older offset-based `query()` still exists for non-cursor callers.
- `revertable_flags` is a cheap, mostly-static per-row property for the list. It does a single batch `ConfigRevision` prev-revision lookup. The authoritative stale/conflict check happens at revert time (409), not here.
