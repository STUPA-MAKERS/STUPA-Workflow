# Applications — `backend/app/modules/applications`

**Does:** Full application lifecycle: anonymous/logged-in submission, versioned `data` edits with structured diffs, status timeline, internal/public comments, list/export/search, and DSGVO Art. 17 anonymization. Every read/write route accepts two identities (`A/P`): a session Principal with the permission, or the applicant with a scoped magic-link token.

**Key files:**
- `models.py` — SQLAlchemy tables: `Application`, `Applicant` (separated PII), `SubmissionVersion`, `StatusEvent`, `MagicLink`, `ApplicationShare`, `Comment`, `GuestApplicationSettings`.
- `guest_settings.py` — `load_guest_settings` (read-only, defaults when the row is missing) and `GuestSettingsService` (get/update + `config_change` audit without revert) for the single row `guest_application_settings` (Z1).
- `router.py` — the `applications` APIRouter. It holds all `/api/applications…` routes, payload caps, magic-link and comment mail background tasks, xlsx export, and erasure-request.
- `service.py` — `ApplicationsService`: `create`/`patch`/`get`/`delete`/`timeline`/`versions`/`list_applications`/`list_tasks`/`add_comment`/`list_comments`/`anonymize`. It validates against the application's *pinned* form version, syncs the promoted `amount`, and resolves state colors from the active global flow.
- `access.py` — `Access` dataclass plus the `require_app_read`/`require_app_edit` deps. It merges Principal-permission, applicant magic-link scope, owner (`created_by`), and Gremium read-scope into one access object. `resolve_app_read` is the one read resolution; `require_app_read` and the attachment routes of `files` call it. The Gremium read scope comes before the owner path. `Access.via` records the path (`permission`/`applicant`/`owner`/`committee`), and `Access.is_applicant_view` is true for the magic link and for the owner path without a member right. `can_read_pii(db, access)`, `principal_reads_pii(principal)` and `hidden_pii_keys(db, access)` hold the PII rule (O21). It exposes `READ_ALL_PERMISSION`/`EDIT_ANY_PERMISSION`.
- `share.py` — `ShareService` (create/resolve/revoke/list_for) plus `build_public_view`, which reduces an application to the fixed `PublicApplication` shape a public page may show.
- `share_page.py` — the hand-written HTML for `/s/{token}`, with the OpenGraph tags a chat client reads.
- `share_router.py` — the public `GET /s/{token}` route. Mounted at the ROOT, outside `/api`.
- `diff.py` — pure `compute_diff` / `is_empty_diff` (added/removed/changed, value-wise, no recursive cell diff).
- `schemas.py` — camelCase Pydantic v2 request/response models (`ApplicationCreate`, `ApplicationOut`, `ApplicationPatch`, `StateOut`, `TimelineEventOut`, `VersionOut`, `ApplicationListItem`, `CommentCreate`, `CommentOut`, `ApplicantOut`). Read-model fields: `stateSince` on `ApplicationOut` and `ApplicationListItem` (A9), `transitionLabel` on `TimelineEventOut` (A3), `changedKeys` on `VersionOut` (A11; `data` and `diff` are nullable), `hiddenKeys` on `ApplicationOut` (O21: the `isPII` keys that the server removed from `data`).

**Domain / data model:**
- `application` — `type_id` (FK application_type), pinned `form_version_id` + `flow_version_id`, `current_state_id`, `gremium_id`, flat `budget_pot_id` plus tree `budget_id`/`fiscal_year_id` (set at budget assignment, movable via move-fiscal-year), promoted `amount`(Numeric 12,2)/`currency`(CHAR 3) synced from `data`, `data` JSONB (GIN `jsonb_path_ops`), `lang`, `created_by` (OIDC `sub` of the logged-in creator, NULL=anonymous), `email_confirmed_at` (an unconfirmed submission stays invisible until the magic-link verify, and the worker discards it after `guest_application_settings.confirm_ttl_hours`; a logged-in submission with the account email is confirmed immediately, with another email it is unconfirmed, F23).
- `applicant` — 1:1 separated PII (`email` CITEXT, `name`), `anonymized_at`, FK `ondelete=CASCADE`. Anonymize sets email and name to NULL and stamps `anonymized_at`. It keeps the application and is **not** a hard delete. Hard delete is the default erasure path.
- `application_share` — a public read-only link. The DB stores only `HMAC-SHA256(pepper, token)`, like `magic_link`, and never the plaintext. `expires_at` (1–365 days, default 30) plus a nullable `revoked_at`; NOT single-use, because several people are meant to open it. `created_by` is the OIDC `sub`, `label` a note for its creator.
- `submission_version` — versioned `data` snapshot plus `diff` JSONB, `UNIQUE(application_id, version)`, v1 at create, `changed_by`.
- `status_event` — timeline entry per transition: `from_state_id`/`to_state_id`/`transition_id`, `actor`, `note`, `at`.
- `magic_link` — the DB stores only the `sha256(token||pepper)` hash. Fields: `scope` CHECK `IN ('edit','view')` (new rows always `edit`, O3), `expires_at` (nullable = no expiry, CHECK `expires_at IS NOT NULL OR scope = 'edit'`), `single_use`/`used_at` (new rows `false`), and a unique token-hash index that carries the atomic single-use redemption of old rows. See `be-auth` for the redeem and expiry rules.
- `guest_application_settings` — single row (`id = 1`): `confirm_ttl_hours` (default 12, CHECK 1..720), `link_ttl_days` (NULL = no expiry, else > 0), `updated_at`, `updated_by`. Maintained at `GET/PUT /api/admin/guest-settings` (`admin.deadlines`, see `be-admin`).
- `comment` — `author_kind` CHECK `IN ('principal','applicant')`, `visibility` CHECK `IN ('internal','public')`. Applicants read and write only `public`.
- States: `state.kind` (`normal`/`vote`/`approval`…), `state.edit_allowed` (edit-lock), `is_initial`, `config.gremiumId` for vote-states. There is exactly ONE active global flow (per-type flows removed, #28). A missing flow gives 404.

**API surface:**
- `POST /api/applications` — public create (anti-abuse: payload cap 413, rate-limit 429, Altcha unless authenticated). It separates PII, writes v1, and enqueues the edit-scope magic-link mail. A guest submission rests in the flow until the magic-link verify: no deadline, no automatic transition, no flow mail (O14). A logged-in submission is confirmed at once only when `applicantEmail` equals the account email (case-insensitive); then the create calls `FlowService.start_confirmed` with the route dispatcher. A logged-in submission for another address rests like a guest submission and needs the magic-link verify (F23). Every create writes the audit `application_create` (type, gremium, initial state, `emailConfirmed`, number of bound drafts; no PII; F12). Optional `attachmentIds` + `draftToken` bind the draft uploads of the wizard (`POST /api/apply/attachments`, Z4) in the create transaction (`files/drafts.py`: `check_drafts`, `bind_drafts`). A missing, expired, foreign or infected draft, a list without a token, or a `file` field value that is not in `attachmentIds` answers 422 and writes nothing. A pending scan is allowed. The router passes `settings.magic_link_secret` as `draft_pepper`. Without the two fields the create is unchanged, and the upload after the create still works.
- `GET /api/applications` — Principal list. Filters: `state/gremium/type/topf/budget/q/amountMin/amountMax/createdFrom/createdTo`, `sort`/`order`, `mine`. `state` repeats (`?state=a&state=b`, A4); one value works as before, an invalid UUID answers 422. Users without `application.read` fall back to the owner and Gremium read-scope. For them `q` does not search the `isPII` values of another application (`hide_pii_in_search`, O21). Each item carries `stateSince` (A9).
- `GET /api/applications/tasks` — open tasks for the Principal (vote-state membership or firable manual transition, own applications too). Each task carries `stateSince`.
- `GET /api/applications/export.xlsx` — needs `application.export`. Same filters (also the repeated `state` and the tri-state `archived`, default `false`), hard cap `EXPORT_MAX_ROWS=10_000` → 413. The export is audited. The workbook holds no form field values (so no `isPII` field) and has the column "Status seit".
- `GET /api/applications/{id}` — A/P read. It sets `canEdit`/`isOwner` and `stateSince` (the status page of the applicant reads it too). The applicant block goes to a principal with the PII right only. `data` drops the `isPII` fields for a reader without the PII right (O21, see below).
- `GET /api/applications/{id}/form` — effective form from the *pinned* version.
- `PATCH /api/applications/{id}` — A(edit)/P. A `data` change writes a new version plus a diff. A locked state gives 409 unless the caller holds `application.edit_any`. An editor without the PII right (for example `application.manage` alone) cannot change the `isPII` fields: the patch keeps their stored values and ignores the sent ones, and the response leaves them out. A validation error on an `isPII` field (a required value that is missing, for example) does not stop that editor.
- `DELETE /api/applications/{id}` — **admin only**, irreversible (manager/creator cannot).
- `POST` / `DELETE /api/applications/{id}/archive` — needs `application.archive`. Reversible and destroys nothing: the application stays fully readable, it only leaves the working list. Archiving expires every magic link of the application (Z1); un-archiving revives none. The applicant can still request a new link for an archived application (archive ends the links, not the access; see `be-auth`). `archived_at` is a timestamp, not a flag. The list filter is a tri-state (`archived=false|true|all`, default `false`).
- `POST` / `GET` / `DELETE /api/applications/{id}/shares[/{share_id}]` — needs `application.share`. Mint, list and revoke public links. The POST response is the ONLY place the plaintext token ever appears; a listing returns `url: null`.
- `GET /s/{token}` — **public, unauthenticated, outside `/api`**. Server-rendered HTML for one shared application.
- `GET /api/applications/{id}/timeline` — A/P status history. Each event carries `transitionLabel` (A3), null for the creation event and for a revert. The applicant view names the Gremium as the actor (A12).
- `GET /api/applications/{id}/versions` — A/P (`require_app_read`). The applicant view (magic link, or a creator who is no member) gets the metadata only: `version`, `at`, `changedKeys`, `changedBy`; `data` and `diff` are null (A11, O17). A principal with the PII right gets `data`, `diff` and `changedKeys`. A Gremium reader gets them without the `isPII` fields (O21).
- `POST /api/applications/{id}/comments` — A(public)/P. It triggers comment mails. Applicants may write only `public` comments. So may a creator who is no member (`Access.can_see_internal` is false on the owner path without a member right).
- `GET /api/applications/{id}/comments` — A/P. Applicants and a creator who is no member see only `public` comments. The applicant view names the Gremium as the author of a member comment (A12).
- `POST /api/applications/{id}/erasure-request` — DSGVO Art. 17 request → privacy queue, and it notifies the data-protection officers (202).

**Conventions & gotchas:**
- Validation runs **before** any DB write (422, not 500). It always uses the application's *pinned* `form_version_id` plus the pot `BudgetField`s, not the currently-active form (data-model §4). On PATCH you must prepend the synthetic system `title` field. If you do not, `_whitelist` drops it and the data is lost.
- Create and patch **strictly whitelist** `data` to known field keys. They discard unknown keys, because the public POST must not stash arbitrary GIN-indexed junk.
- `extract_promoted` promotes `amount`/`currency` out of `data` (default currency EUR) and re-syncs them on every patch.
- Every PATCH writes an `application_update` audit entry in the same transaction: `{version, changedFields}` with the keys of the added, removed and changed fields, never the values (F12). The version diff keeps the values.
- The first magic-link verify sets `email_confirmed_at` and starts the resting flow (`auth.service.verify_magic_link` → `FlowService.start_confirmed`: deadline, `auto_advance`, task mail). The new-application task mail therefore reaches the staff only after the confirmation. A second verify starts nothing.
- After the commit a PATCH re-creates the flow deadline when the policy of the current state is `relative_changed` (F7, `state_deadline_follows_edits` + `FlowService.schedule_state_deadline`).
- Access is dual: `require_app_read`/`require_app_edit` resolve Principal-permission OR magic-link scope OR `created_by` owner (#24) OR Gremium read-scope. `_committee_read_clauses` (list) and `_committee_can_read` (detail) **must stay mirrored** (budget view-scope subtree from the `path_key` prefix, vote-state `config.gremiumId`, historical meeting vote). `application.read_all`/`application.edit_any` bypass scope and lock.
- Anonymize scrubs ALL PII vectors: the applicant row, the current `data`, every `submission_version.data` and its stored `diff`. It also deletes magic-links and attachments (through `FilesService` when present). It unions the `isPII` keys across *all* form versions of the type, not only the pinned one. A field marked PII later must still be erased.
- The share routes are **two different decisions**. Creating a link is gated on `application.share`, deliberately NOT on the read permission: someone reading through a magic link must not be able to publish. Opening a link is unauthenticated and does NOT go through `resolve_access` — that function answers "may this principal read this?", and here there is no principal, so reusing it would mean inventing one.
- A share token that is unknown, expired or revoked all answer the same **404**, never 410. "This link expired" tells a stranger they found a real one and were only too late.
- The public view drops every field marked `is_pii`, reading the SAME definitions the PDF renders from through `_field_from_row`. Two readers of one definition cannot drift into disagreeing about what counts as personal. Comments and version history stay off the page entirely.
- The OpenGraph preview carries the **title only**. That text lands permanently on a chat server we do not control; a preview saying "€4,200, rejected" has published a decision to everyone in the room before anyone opened the link.
- `ShareService.create` flushes, it does not just `add`. `id` and `created_at` are server defaults, so without the flush the response model has nothing to serialize.
- nginx proxies `/s/<token>` to the API **ahead of the SPA fallback** (`deploy/web/nginx.conf`). Without that location the Angular shell swallows the path and every link preview shows a bare URL.
- Concurrent PATCH hitting the same `version` (UNIQUE) → caught `IntegrityError` → 409 retry, not 500.
- Never surface raw UUIDs or stored keys in the UI. `_resolve_actors` turns the stored actor values of the timeline, the versions and the comments into `ActorOut` (`actorInfo`, `changedByInfo`, `authorInfo`): `kind` is `principal` (name or email), `applicant`, `system` (`key` from `system:<key>`, plain `system` gives `auto`), `gremium` (applicant view) or `deleted` (unknown or anonymized account). It reads all names in one query through `_author_names`, which never falls back to the `sub`. The legacy string fields (`actor`, `changedBy`, `author`) stay for API clients and carry no raw `sub` either. The frontend renders `shared/actor-label.util.ts` (see [[no-uuids-in-ui]]). The service resolves state colors from the active global flow by `key` (old state rows carry `color=NULL` after a flow re-save).
- **PII rule (O21).** The PII right is `application.read`, `application.read_all` or admin (`Principal.has`, so the OAuth scope cap applies). The applicant (magic link) and the logged-in creator read the own data. Everybody else, above all a Gremium reader without `application.read`, gets the detail, the versions and the archive responses without the `isPII` fields and without the applicant block. The key set is `_pii_keys_for_type`, the union over every form version of the type, as for the anonymization. `ApplicationOut.hiddenKeys` lists the removed keys, and the frontend edit form leaves out exactly these fields (a key that is only missing from `data` was never answered and stays editable). The attachments of an `isPII` field are hidden too: `GET /applications/{id}/attachments` leaves them out, and `GET /attachments/{id}[/download]` answers 404. An attachment belongs to such a field when its `field_key` names the field or the answer of the field refers to its id. The search `q` of the list, of the XLSX export and of the global search skips the `isPII` values for such a reader: `_search_text` reads `data` minus the union of all `isPII` keys of all types (`_all_pii_keys`), and keeps the full `data` for the own applications. That projection does not use the trigram index.
- **Applicant view (A12, O16).** `Access.is_applicant_view` is true for the magic link and for the owner path when the creator is no member. A creator is a member when the creator reads through the Gremium read scope (that path comes first, so `via` is `committee`), or holds `application.manage`, `application.transition` or `application.edit_any` (`_MEMBER_PERMISSIONS`). A member sees the internal comments, the names and the full versions. Then the timeline actor, the version editor and the author of a member comment are the name of the Gremium of the application (`_gremium_actor`; null without a Gremium). The own actions keep the applicant: the actor `applicant` and the `sub` of the creator (`_applicant_actors`). In the magic-link view the creator `sub` counts as the applicant only when the account email equals the applicant email (case-insensitive). A creator who submitted for another email (F23) is a member like any other, so the applicant sees the Gremium. A member who reads through a permission or the Gremium read scope still sees the names.
- **`stateSince` (A9).** `state_since_subquery()` is one grouped subquery `max(status_event.at)` per application. The list joins it with an outer join. The tasks and the detail use `_state_since_map`. Without a status event the value is `created_at`.
- All error paths return `application/problem+json` (RFC-9457). Guards and validation use whitelist dispatch, never eval (see the `conventions` skill).
