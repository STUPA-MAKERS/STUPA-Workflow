# Admin / Config Surface — `backend/app/modules/admin`

**Does:** Server-authoritative CRUD for the platform config. It covers gremien with their per-gremium roles and the three separate OIDC group mappings that derive the global roles and the memberships, application-types, and the one global flow version. It also covers RBAC (roles, role-assignments, group-mappings, principal activation), webhooks, and versioned branding/site-config with a draft→activate lifecycle. Every mutation writes an audit entry in the same transaction. Config-versioned entities (flow, site-config) also snapshot to `config_revision`.

**Key files:**
- `router.py` — three routers: `router` (prefix `/admin`, per-page permission gates), `public_router` (auth-free `/site-config` + `/manifest.webmanifest`), `authed_router` (auth-only `/gremien` dropdown source, no admin right). Declares all per-page permission `Depends` constants.
- `service.py` — `ConfigService`: gremien, application-types, global flow version, roles/assignments/group-mappings/principals, webhooks. Mapper helpers at bottom.
- `site_config_service.py` — `SiteConfigService`: branding draft/activate/restore + `public()` + `manifest()` (dynamic PWA manifest, single source of truth).
- `gremium_roles.py` — `GremiumRoleService` (per-gremium roles, read-only membership list) plus RBAC resolver helpers `active_gremium_roles`, `gremium_ids_for` (scope-capped, for every request path), `admin_bypass` (admin role + scope cap), `gremium_ids_with_permission` (sub-based, only for system and roster paths), `gremium_member_ids`, `intervals_overlap`, and `FORCED_GREMIUM_ROLES`.
- `branding.py` — `Branding` Pydantic schema: logos (image-only, no SVG, magic-byte sniffed, 2 MB cap), footer columns/links, legal links, i18n freetexts, and the switch `gravatarEnabled` (default `True`; off makes the avatar proxy answer 404, see `be-avatars`). The security contract lives here.
- `cd_logos.py` — corporate-design logo policy: the vendored logo names (shipped by the typst service), the slot/base-variant value sets, the upload allowlist (PNG/JPEG/WebP/**SVG**/**PDF**), `sniff_cd_logo`, `asset_file_name`.
- `cd_resolver.py` — the render seam: `ResolvedCdVariant` + `resolve_cd_variant(db, storage, gremium_id)` and `cd_variant_key_for_gremium`.
- `service/cd_variants.py` — `CdVariantService`: variant CRUD, logo upload/vendored/reorder/delete, logo download bytes.
- `oidc_mappings.py` — `OidcMappingService`: CRUD for the gremium membership mappings and gremium role mappings; each write audits, runs `sync_all_memberships`, commits.
- `membership_sync.py` — `sync_principal_memberships` / `sync_all_memberships`: the ONLY writer of `gremium_membership`. Runs at OIDC login (`auth/service.oidc_callback`), after each mapping change (all principals), at principal erasure and at an account merge. A merged principal (`merged_into` set) counts as without groups, so it holds no membership.
- `principal_merge.py` — `PrincipalMergeService` (account merge, "Konten zusammenführen"): `preview(old, new)` counts per area what a merge rewrites, combines and removes, and lists the real conflicts; `merge(old, new, actor=)` runs the same checks under `FOR UPDATE` locks and applies everything in ONE transaction, then commits. `SUB_COLUMNS` / `ID_COLUMNS` / `REMOVED_ROWS` list every column that references a principal. A new column that stores a principal `sub` or id MUST go into one of these lists (or into a combine step), else a merge leaves it on the old account.
- `models.py` — SQLAlchemy: `CdVariant`, `CdVariantLogo`, `Gremium`, `GremiumRole`, `GremiumGroupMapping`, `GremiumMembership`, `MailList`, `ApplicationType`, `Webhook`, `WebhookDelivery`, `SiteConfigVersion`.
- `schemas.py` — camelCase DTOs (`populate_by_name`, `serialization_alias` on Out models).

**Domain / data model:**
- `cd_variant` / `cd_variant_logo` — admin-managed corporate-design variants. A variant holds only a `key` (slug, unique, **immutable**), a display `name` and a `base_variant` (`report`/`protocol`). Its logos live in `cd_variant_logo`: one row per logo, in a `slot` (`title`/`footer`) at a `position`. A row is EITHER a vendored logo name OR an uploaded MinIO object (`object_key`/`file_name`/`mime`/`size`) — a DB CHECK holds that exactly-one-of rule. Colors and fonts are NOT part of a variant.
- `gremium` — a Gremium (student-government body). `slug` unique, `cd_variant_id` (FK → `cd_variant`, RESTRICT, nullable), `default_lang`, vote-delegation knobs (`allow_vote_delegation`, `delegation_lead_minutes`, `delegation_allow_external`), `quorum_percent` (0–100, nullable, explicitly clearable via `model_fields_set`). The service seeds the forced gremium-roles when it creates a gremium.
- `gremium_role` — per-gremium role set, **separate** from global `role`. `(gremium_id, key)` unique. `permissions` JSONB from the 5-key gremium catalog `GREMIUM_PERMISSIONS`: `session.manage`, `vote.manage`, `vote.cast`, `protocol.write`, `protocol.finalize`. `_sanitize_perms` drops every other key (bug F4: before, it stripped `protocol.finalize`). Forced roles `vorstand`/`manager` (all 5) and `member` (vote.cast only) exist in every gremium. Migration `3a0b9672fcba` gave `protocol.finalize` to the existing `vorstand`/`manager` rows. Migration `b0c8fd389e10` gave it to every other role that held `session.manage`. A role that you create later gets it only by hand. The global `meeting.manage`, `protocol.finalize` and `application.create` are gone from `PERMISSION_CATALOGUE`. Nobody can delete them, and the list route backfills them lazily.
- `gremium_membership_mapping` — OIDC group → membership in one gremium (`oidc_group`, `gremium_id`, unique pair, 409 on duplicate). `oidc_mappings.OidcMappingService`.
- `gremium_role_mapping` — OIDC group → a role of one gremium (`gremium_role_id`, `oidc_group`, unique pair). Applies ONLY to a member via a membership mapping; never grants membership. Role FK `RESTRICT` (a mapped role cannot be deleted, 409). Global roles, gremium membership and gremium roles are unrelated — never combine them in one mapping.
- `gremium_membership` — DERIVED from `principal.oidc_groups` × the two gremium mappings. Member ⇔ a membership mapping matches. Role = best matching role mapping of that gremium (more permissions, then lower key), else the forced `member` role. No manual write path, no term of office (`valid_from`/`valid_until` stay NULL; readers still filter on them). One row per (principal, gremium), backed by the EXCLUDE constraint. IdP changes take effect at the next login. Migration `097f61e33e3c` deleted all older rows.
- `application_type` — `key` unique, `name_i18n`, `has_budget`, `comparison_offers` JSONB, `retention_months` (DSGVO, nullable=global default), `active_form_version_id` (circular FK, use_alter). Delete is 409 if any application references it.
- `mail_list` — per-gremium recipients. The canonical `name='protocol'` row holds extra protocol recipients (PUT replaces all rows).
- `webhook` — `name/url/events` (whitelist `EventName`), server-generated `secret` (32 bytes, HMAC signing, never returned), `active`. `webhook_delivery` — worker-written. Status pending/ok/failed/dead, unique `(webhook_id, idempotency_key)`, pickup index `(status, next_at)`.
- `site_config_version` — versioned branding. `version` unique, partial-unique one `active` row (`WHERE active`), `branding` JSONB, `created_by`=OIDC sub. Draft = latest inactive version. Activate flips `active`.
- Global flow: there is exactly **one** flow for all types (`flow_version` etc. live in the `flow` module). Each save creates a new immutable version. That save re-pins ALL running applications by state **key** to the newest version (dropped keys → initial state). The system never deletes a version.
- RBAC rows (`role`, `role_permission`, `role_assignment`, `group_mapping`, `principal`) live in the `auth` module. The admin module only does their CRUD.

**API surface:**
- `GET /api/admin/config-schemas` — JSON-schemas for FE editors (any admin area).
- `GET|POST /api/admin/gremien`, `PATCH|DELETE /api/admin/gremien/{id}`, `GET|PUT /api/admin/gremien/{id}/mail-recipients` — gremien CRUD + protocol recipients (admin.gremien). The list (`GremiumAdminOut`) also gives `memberCount` (distinct members) and `roleCount` (gremium roles, forced ones included) from two grouped counts (`list_gremien_admin`), so the admin overview needs no request per gremium. The public `GET /api/gremien` has no counts.
- `GET|POST /api/admin/gremien/{id}/roles`, `PATCH|DELETE /api/admin/gremium-roles/{id}` — per-gremium roles (admin.gremium_roles to write, admin.gremien may also list).
- `GET /api/admin/gremien/{id}/memberships` — read-only derived memberships with `displayName`, `email` and `active` of each member (outer join on `principal`; `active` = active principal and valid now, the rule of the `memberCount` in the gremien list; the members page and the pool show only active rows), so a members page needs no principal list (the principal list stops at 50 rows). Gate `_MEMBERSHIP_READERS`: admin.gremien or admin.delegations (the substitute pool on the delegations page needs the members).
- `GET|POST /api/admin/gremium-membership-mappings`, `PATCH|DELETE .../{id}` and `GET|POST /api/admin/gremium-role-mappings`, `PATCH|DELETE .../{id}` — the gremium mappings (admin.group_mappings; every write re-syncs all principals). `vote:` prefix → 422. All three mapping kinds live on the one page `/admin/group-mappings`.
- `GET /api/gremien` — auth-only gremien dropdown source (no admin right, `authed_router`).
- `GET|POST /api/admin/cd-variants`, `PATCH|DELETE /api/admin/cd-variants/{id}`, `POST /api/admin/cd-variants/{id}/logos` (multipart), `POST .../logos/vendored`, `PUT .../logos/order`, `GET|DELETE /api/admin/cd-variant-logos/{id}[/file]` — CD variants (admin.cd_variants). Delete answers 409 while a Gremium references the variant; a key change answers 409.
- `GET /api/cd-variants` — slim option list `{id, key, name}` for the Gremium dropdown (`admin.gremien` OR `admin.cd_variants`, `authed_router`).
- `GET|POST /api/admin/application-types`, `PATCH /api/admin/application-types/{id}`, `DELETE` (admin.types, delete needs admin.types_delete). `ApplicationTypeOut.activeFormVersion` is the number of the active form version (`null` while none is active); the list gets it with one outer join on `form_version`, so the admin forms list needs no request per type.
- `GET|POST /api/admin/flow-versions/global` — read/create the single global flow (read also allowed to flow.configure/budget.structure).
- `GET /api/admin/principals` (gate `_PRINCIPAL_READERS`: admin.gremien, admin.users or admin.delegations, for the person picker of the substitute pool), `PATCH /api/admin/principals/{id}` (activate/deactivate), `GET /api/admin/permissions` (key catalog), `GET|POST /api/admin/roles`, `PATCH|DELETE /api/admin/roles/{id}` (admin.roles, admin/member protected).
- `GET /api/admin/principals/{id}/merge-preview?targetId=`, `POST /api/admin/principals/{id}/merge` (body `{targetId}`) — account merge, gate `admin.users.merge` (only the admin role by default; no OAuth scope carries it, so an agent token never merges). `{id}` is the old account. The merge rewrites every reference from the old `sub`/id to the new one, combines harmless duplicates (notification preference, pool entry, equal attendance; the row of the new account wins, a pool entry in which one account substitutes for the other goes), removes the sessions, OAuth codes and tokens, the feed token, the role assignments (rights never move; the new account gets its roles from OIDC and the bootstrap) and the derived memberships of the old account, and sets `merged_into`/`merged_at`/`active=false` on the old row. Real conflicts give 409 `merge_conflict` with `errors: [{field: kind, msg: label}]`: `ballot_same_vote` (open ballot or voted marker of both in one vote), `delegation_same_meeting`, `delegation_vote_twice`, `delegation_chain`, `attendance_differs`, `erasure_open`. Other refusals: 422 `merge_same_principal`, 404, 409 `principal_already_merged` / `merge_target_merged` / `merge_target_inactive` / `merge_own_account` / `principal_erased` (an executed erasure request or a `principal_erased` audit entry for either side, checked under the lock) / `merge_retry` (deadlock 40P01 or serialization failure 40001). **Privileges (security review D1):** the effective rights of the old account (global permissions, `key@<gremium>` for gremium roles, `*` for the admin role) that the new account lacks are `extraPermissions` in the preview; the merge refuses with 409 `merge_privileges` unless the acting admin holds all of them (`actorHoldsExtra`). Merging the own old account into the own account is the main use case and is allowed. The audit `data` lists `extraPermissions`. A guard test (`tests/unit/modules/admin/test_principal_merge_guard.py`) scans `Base.metadata` and fails for a principal column that is not in `SUB_COLUMNS`, `ID_COLUMNS`, `REMOVED_ROWS`, `COMBINED_COLUMNS` or `EXCLUDED_COLUMNS`. The append-only tables (`audit_entry`, `config_revision`) keep the old `sub`; their displays resolve it through `auth/identity.py`. `secret_ballot` is never read. The merge writes the audit action `principal_merge` (ids and counts only). `PATCH /api/admin/principals/{id}` refuses to activate a merged account (409 `principal_merged`). `PrincipalOut` carries `mergedIntoId`, `mergedIntoName`, `mergedAt`.
- `GET /api/admin/role-assignments` — read-only (admin.users). Only bootstrap rows exist (`admin` from `BOOTSTRAP_ADMIN_*`, implicit `member`). Global roles come from `group_mapping`. `GET /api/admin/principals` carries `oidcGroups`.
- `GET|POST /api/admin/group-mappings`, `PATCH|DELETE /api/admin/group-mappings/{id}` — OIDC group → global role, NO gremium scope (admin.group_mappings).
- `GET|POST /api/admin/webhooks`, `PATCH /api/admin/webhooks/{id}` (webhook.manage, list also flow.configure).
- `GET /api/admin/site-config`, `PUT /api/admin/site-config/draft`, `POST /api/admin/site-config/activate` (admin.site).
- `GET`, `PUT /api/admin/guest-settings` (admin.deadlines) — the single row `guest_application_settings` (Z1): `confirmTtlHours` (1..720) and `linkTtlDays` (null = magic links without expiry, else 1..3650). PUT is a full replacement and writes `config_change` (target `guest_application_settings`, old/new values) WITHOUT a revision, so the audit log offers no revert. The service lives in `applications/guest_settings.py`.
- `GET /api/site-config` (auth-free public branding plus `confirmTtlHours` and `linkTtlDays` for the wizard confirmation page and the status page, and `attachmentLimits` (`maxFileBytes`, `maxDraftFiles`, `maxDraftBytes` from the settings of the draft upload, Z4) for the text below the wizard drop zone; `Cache-Control: public, max-age=300`), `GET /api/manifest.webmanifest` (auth-free dynamic PWA manifest).

**Conventions & gotchas:**
- **Role keys (A10):** `RoleCreate.key` and `GremiumRoleCreate.key` must match `ROLE_KEY_PATTERN = ^[a-z][a-z0-9_]*$` (schemas.py), else 422. The update schemas carry no key, so a key never changes. Migration `373c9fe9cafb` only LOGS the existing `role`/`gremium_role` keys that break the pattern and changes none. The FE mirrors the pattern as `ROLE_KEY_PATTERN` in `pages/admin/admin.models.ts`: both create dialogs show the rule and disable save for a key that breaks it. Keep the two patterns the same.
- **One permission per admin page.** Migration 0017 split `admin.config` into `admin.gremien/.types/.site/.roles` (`admin.roles` itself predates that migration). A later per-page split added `admin.users/.group_mappings/.gremium_roles/.delegations/.deadlines`. Reads shared across pages use `require_any_permission(...)`, for example `_FLOW_READABLE`, `_ROLES_READ`, `_PRINCIPAL_READERS` and `_MEMBERSHIP_READERS`. Writes always gate on the strict key. The router enforces RBAC through `require_principal`. The FE is UX only.
- Two **separate** role systems exist: global `role`/`role_assignment` (39-permission catalog from `app.shared.permissions.PERMISSION_CATALOGUE`) and `gremium_role` (the fixed 5-key catalog `GREMIUM_PERMISSIONS` of `gremium_roles.py`: session.manage, vote.manage, vote.cast, protocol.write, protocol.finalize; resolved from the active membership). Do not conflate them. See [[admin-domain-rules]] (admin = all rights, vote-delegation is per-gremium).
- Self-lockout guard: an admin cannot deactivate their own account. Role assignments have no write API any more, so the old assignment guards are gone. Break-glass admin access: `BOOTSTRAP_ADMIN_SUBJECTS/EMAILS` (env) or `admin-cli`.
- Config versioning: a flow save (`create_global_flow_version`) and a branding activate write a `config_revision` snapshot plus a linked audit entry. The revert/restore path replays that snapshot (`restore_branding`, `create_global_flow_version(action=...)`). See [[revert-feature-scope]] and `be-config-revision`.
- Every save of the global flow re-pins ALL applications by state **key**, so the pin is not version-based. Removed keys fall back to the single initial state. Deactivate the old active version before you insert the new one (partial-unique `WHERE active`).
- The server validates branding logos from decoded magic bytes (PNG/JPEG/WebP/ICO whitelist). It refuses **inline SVG** (XSS) and checks the real byte size against the 2 MB cap, because the client `size` is untrusted. Footer and legal URLs reject `javascript:`/`data:`/`vbscript:`. i18n freetexts have length caps (auth-free public read).
- **CD logos are the one exception that accepts SVG and PDF**, because those bytes only ever reach the typst render service, never the browser. The price: `GET /api/admin/cd-variant-logos/{id}/file` MUST answer `application/octet-stream` plus `Content-Disposition: attachment` and must never echo the stored `mime` — the same rule as `get_invoice_file` in `be-budget`. `cd_logos.sniff_cd_logo` reuses `branding.sniff_raster_image`; do not widen the branding sniffer.
- The server generates `webhook.secret` and never serializes it in any Out DTO.
- All datetimes are tz-aware UTC. `_parse_dt` normalizes them, and assignment `valid_from/until` are timestamptz from the schema baseline. All error paths return `ProblemDetail` (problem+json): 400 malformed JSON, 422 schema, 404 not-found, 409 conflict.
- camelCase JSON comes from `_CamelModel` (`populate_by_name=True`). Out models use `serialization_alias`, In models use `alias`. Nullable-clearable fields (`quorumPercent`, `retentionMonths`) tell "absent" from "null" through `payload.model_fields_set`.
- Webhook persistence lives in this module on purpose (not in `modules/webhooks`) because admin CRUD is the only writer of the config. The delivery worker sits in `webhooks`. See `be-webhooks`.
- `form-versions`, `notification-rules`/`mail-templates`, and `/admin/audit` are NOT here. They live in the forms, notifications, and audit modules.
