# Flow / Status Engine — `backend/app/modules/flow`

**Does:** Runs the global declarative state machine that every application moves through. It evaluates guards, fires transitions atomically with audit and worker actions, and lists the firable transitions for a principal. The admin module stores and edits the graph itself (states and transitions). This module is the runtime engine.

**Key files:**
- `service.py` — `FlowService`: `available_transitions`, `fire`, `auto_advance`, `fire_branch`/`branch_transition`, `available_applicant_transitions`/`fire_as_applicant`, `start_confirmed`, `revert_status`. The CRITICAL core.
- `context.py` — `build_context()`: assembles the pure `GuardContext` from the DB (actor Gremien, applicant roles and Gremien, budget fit, field values and types).
- `dispatch.py` — `DispatchedAction`, `build_dispatched_actions` (worker whitelist filter), `build_implicit_notifications` (auto applicant + task mail), `ActionDispatcher` protocol, `NullActionDispatcher` (log-only default), `ChainActionDispatcher`, `build_worker_dispatcher(redis, sessionmaker, settings)` (the full chain: notify, webhook, extras).
- `extras_dispatcher.py` — `FlowExtrasActionDispatcher`: in-process handlers for `addToNextSession`, `assignBudget` and `assignBudgetFromField`. The budget assignment is idempotent: a retry that finds the cost center set changes nothing and writes no second audit entry.
- `router.py` — the application-transition routes. `MANAGE_PERMISSION = "application.transition"`. `get_action_dispatcher` is THE dispatcher dependency: `app.main` overrides it with `build_worker_dispatcher`, and the voting and live-vote routers depend on it too. Never add a second local dispatcher dependency: the override would not reach it.
- `models.py` — `FlowVersion`, `State`, `Transition` tables.
- `vote_gremium.py` — the vote Gremium snapshot: `resolve_vote_gremium`, `snapshot_for_entry` (409 `no_vote_gremium`, fail closed), `gremium_from_budget`, `in_budget_vote_state`.
- `schemas.py` — `TransitionOut` (with `addsToAgenda`, `agendaGremiumId`), `TransitionRequest` (with optional `meetingId`, `nonPublic`), `TransitionResult` (camelCase aliases).
- `../../shared/guards.py` — the pure guard evaluator + whitelists + `validate_guard`/`validate_action` (lives in `app/shared`, not in this module).
- `../../shared/config_schemas.py` — `FlowGraph` + `validate_flow_graph` (the graph save-gate and validator).

**Domain / data model:**
- `flow_version` — the ONE global flow (typed flows removed, migration 0019). Partial-unique `uq_flow_version_one_active_global` → exactly one `active` row. Cols: `version` (unique), `active`, `editor_layout` (JSONB).
- `state` — `flow_version_id` (FK CASCADE), `key`, `label_i18n`, `color`, `edit_allowed`, `is_initial`, `is_terminal`, `kind`, `config` (JSONB). `kind ∈ {normal, vote}` (CHECK `state_kind`, approval and decision removed). One partial-unique `is_initial` per flow. Unique `(flow_version_id, key)`. A `vote` state needs EXACTLY ONE of `config.gremiumId` (fixed) or `config.gremiumSource: "budget"` (the effective deciding Gremium of the cost center, `budget.decision_gremium_id`; not allowed on the initial state).
- `transition` — `flow_version_id`, `from_state_id`, `to_state_id` (all FK CASCADE), `label_i18n`, `color`, `guard` (JSONB | NULL), `actions` (JSONB list), `order`, `automatic` (the worker fires it when the guard is true), `branch` (`pass`/`fail` for vote-state exits, else NULL), `requires_action` (counts as an open task). The edit lock derives from the target `state.edit_allowed`. `applications.patch` handles it inline and returns 409. It is NOT a dispatched action.
- A fired transition writes a `StatusEvent` (in `applications.models`) + a `status_change` audit entry in the same transaction.

**Guard catalog (`shared/guards.py`):** declarative, whitelist, NO eval. `eval_guard(guard, ctx)` takes a single-key dict. An empty guard or None gives True.
- Combinators: `and`, `or`, `not`.
- Conditions (auto + manual): `applicantRoleIs`, `applicantCommitteeIs`, `budgetIs`, `budgetFitsApplication`, `hasField`, `compare` ({field, op, value}, typed by the field type of the pinned form version, fail-closed on a missing field or an unknown op).
- Actor gates (MANUAL only, rejected on automatic transitions by `allow_actor_ops=False`): `roleIs`, `isInCommittee`, `actorIsApplicant`.
- Conditions also: `budgetHasDecisionGremium` (bool). Actor gates also: `isInVoteGremium` (bool, actor is a member of `application.vote_gremium_id`).
- Action whitelist: `webhook` (needs `webhookId`), `notify` (needs `recipients[]` of kind gremium/role/applicant/email/voteGremium/budgetGremium; the last two take no `ref`), `addToNextSession` (optional `gremiumId`, default = the vote snapshot; only on a transition INTO a vote state), `assignBudget` (needs `budgetId`), `assignBudgetFromField` (needs `field`, the form field that holds the cost center id), `assignBudgetFromApplicantGremium` (optional `parentId`; the single node whose OWN deciding Gremium is a Gremium of the applicant, else nothing), `assignBudgetFromMap` (`field` + `map` value→budget id; the admin save checks the ids exist). No `assignBudget*` action on a transition into a `gremiumSource: "budget"` vote state. An unknown operator or action raises `GuardError` at SAVE time (`validate_guard`/`validate_action`/`validate_flow_graph`), not at runtime.

**API surface:**
- `GET  /api/applications/{id}/transitions` — P(`application.transition`) AND read access (`require_transition_principal` calls `resolve_app_read`, else 403). The force routes need `application.force_status` and the read access too (`require_force_principal`). The firable manual transitions. The engine evaluates the guards for the principal and excludes `automatic` and `branch`. `addsToAgenda`/`agendaGremiumId` flag a transition with `addToNextSession` into a vote state (the "put on the agenda" dialog). Only such a transition takes a `meetingId` (`_check_agenda_meeting`); one into a normal state has `addsToAgenda=false` and fires without a meeting.
- `POST /api/applications/{id}/transition` — P(`application.transition`) AND read access, as the list. Fire a transition → 200 `{newStateId, statusEventId, dispatchedActions}` or 409 on a guard, a state conflict, a race, a branch or an automatic transition (the list hides both, so the fire refuses both). Optional `meetingId` + `nonPublic`: before the state change the engine checks that the transition has `addToNextSession`, its target is a vote state, and the meeting is readable, `planned` and of the action Gremium, else 422 `agenda_meeting_invalid`. `AgendaService.add_in_tx` then adds the item in the same transaction (a refusal rolls everything back, 422), and the post-commit `addToNextSession` is skipped.
- `GET  /api/applications/{id}/applicant-transitions` — the magic-link applicant and the logged-in creator only (`access.require_app_applicant`, the same gate as the POST); any other principal gets 403. Only manual transitions gated by `actorIsApplicant`. The status page of the frontend treats the 403 as "no actions".
- `POST /api/applications/{id}/applicant-transition` — fire as applicant. Only the magic-link applicant and the logged-in creator (`access.require_app_applicant`); a principal with `application.manage`/`edit_any` who is not the creator gets 403. 403 unless `actorIsApplicant` opened the transition.
- Flow GRAPH CRUD is NOT here. It lives in the admin module: `GET/POST /api/flow-versions/global` (`AdminService.get_active_global_flow`/`create_global_flow_version`), validated by `validate_flow_graph`.

**Conventions & gotchas:**
- `fire()` uses optimistic locking. The rowcount of `UPDATE … WHERE current_state_id = from_state_id` must be 1, else the call gives 409 for a concurrent transition. Always re-check the state, never assume it.
- Only the vote outcome fires a branch transition (`pass`/`fail`) with `manual=False`. A manual `fire` of a branch transition gives 409, because nobody may set a vote result by hand. The vote close calls `stage_branch` inside a SAVEPOINT (`session.begin_nested()`) and commits the close and the transition ONCE. On a guard failure, a lost race or a missing branch only the SAVEPOINT rolls back, so `stage_fire` takes `rollback_on_conflict=False` there. `fire_branch` (commit included) stays for direct callers.
- `fire` = `stage_fire` (all writes, no commit, returns a `StagedFire`) + commit + `after_commit` (`vote_cancelled` events, worker actions).
- **Leaving a vote state cancels its votes.** A transition without a branch, `force_status` and `revert_status` call `VotingService.cancel_for_application`: every `open` vote of the application and the drafts of the state that the application leaves become `cancelled`, get `closed_at` and a `vote_cancel` audit entry (reason `state_left`). A draft belongs to the left state when its `opens_state_id` is that state, or when `opens_state_id` is NULL and the left state is a vote state (`kind == 'vote'` or a `pass`/`fail` exit). Every other draft stays: a draft without `opens_state_id` survives the transition INTO the vote state, and a draft for a later vote state survives too. A transition back into the same state keeps every draft. After the commit `_publish_cancelled` sends `vote_cancelled` through the optional `MeetingPublisher` (`FlowService(session, dispatcher, publisher)`; the flow router, the audit revert route and the worker pass one). A broker fault only logs. A vote branch cancels nothing, because the close owns the vote.
- `auto_advance` NEVER fires out of a `vote` state. This is fail-closed, and the validator also forbids an automatic non-branch exit from a vote state. Otherwise the engine would approve an application without a vote.
- The engine fills the actor roles and Gremien only for a `manual=True` context. An automatic run sees empty actor sets, so an actor gate cannot pass.
- Worker actions dispatch AFTER the commit. They are idempotent and retryable and carry a stable `idempotency_key`. The engine logs an action failure and swallows it. An action must never roll back the committed state change. `build_dispatched_actions` filters again to the worker whitelist (`notify`, `webhook`, `addToNextSession`, `assignBudget`, `assignBudgetFromField`). It skips `setEditLock` and the rest. Keep `WORKER_ACTION_TYPES` in sync with the validator whitelist: an action missing there never runs.
- Every path that fires runs the full chain: the manual route, `POST /votes/{id}/close`, the live-vote routes (app override) and the worker (`ctx["flow_dispatcher"]`, set in `worker.main._on_startup`).
- `addToNextSession` after the commit takes the earliest meeting of the Gremium with `status = planned` and `date >= today` in `settings.local_timezone`. A live or closed meeting never gets the item. Without such a meeting it only logs.
- The guard `attachmentPresent` counts only attachments with `scanned = true`, `scan_result = 'clean'` and a `storage_key`.
- Every fire emits implicit mails: a `notify` to the applicant and a `taskNotify` to the actors of the new state. An explicit applicant `notify` in the config replaces the implicit one.
- Unconfirmed guest applications (`email_confirmed_at IS NULL`) rest in the flow. The create starts nothing. The auto-transition scan of the cron skips them, and the notify dispatcher sends them no `notify` or `taskNotify` mail. Every flow route passes `allow_unconfirmed=False` to `_load_app`, so such an application gives 404 there. `POST /applications/{id}/votes` (`VotingService.create`) also gives 404 for it. The internal callers (worker, vote close, revert) keep the default `True`.
- `start_confirmed(application_id)` starts the flow one time: it commits the confirmation, then runs `auto_advance` as `system:confirmation`, then the `taskNotify` of the current state when no transition fired (`transition_id=None`, key `{app}:{event}:auto:task`). `verify_magic_link` calls it only when its `UPDATE … WHERE email_confirmed_at IS NULL RETURNING id` matches, so a second click sends nothing. A logged-in create calls it at once. It commits before the dispatch, because the dispatchers read in their own sessions. After that commit, an error of `auto_advance` or of the task mail never fails the verify or the create: as in the cron, the method rolls the session back, logs the error and returns `None`. The cron then tries the automatic transitions again.
- **Worker cron `process_deadlines`** (`worker/deadlines.py`, every minute, name kept for the arq schedule). It runs these steps, each idempotent and each unit locked with `FOR UPDATE SKIP LOCKED` in its own session: (1) vote auto-close: an open vote past `closes_at` (`due_open_vote_ids`, `lock_open_vote`) goes to `voting.close`, which tallies and fires the result branch; a blocked branch still ends the vote (audit `vote_branch_blocked`). (2) automatic transitions: confirmed applications in a state with an `automatic` exit get `auto_advance` (`manual=False`). (3) discard: applications with `email_confirmed_at IS NULL` older than `guest_application_settings.confirm_ttl_hours` (read on every run) are deleted with a `guest_application_discard` audit entry (no PII); the MinIO objects go after the commit, best effort. (4) to-do reminders (`worker/todos.py`) and (5) poll reminders (`worker/polls.py`); a failure there only logs. Every scan takes at most `DEFAULT_SCAN_LIMIT` (200) rows, oldest first. The actor is `system:deadlines` with `application.manage`, and every cron transition uses `ctx["flow_dispatcher"]`, the full chain from `build_worker_dispatcher`.
- `revert_status` (audit-log revert) flips the state back ONLY while the application still sits in `to_state_id`, else 409 `stale_revert`. It cancels the votes of the state it leaves (see above). It does NOT undo other side effects: a cancelled vote stays cancelled, and sent webhooks and mails stay sent. `config_revision.revert` calls it (`RevertService(session, publisher)`).
- **Vote Gremium snapshot (flow variant B).** Every state change (`stage_fire`, `force_status`, `revert_status`) writes `application.vote_gremium_id` in the same `UPDATE` as the state: the Gremium of the target vote state, or NULL for a non-vote target. Every reader of "the Gremium of the vote" reads the snapshot, never `state.config`: committee read scope (`access._committee_can_read`, `listing._committee_read_clauses`, so also the tasks), the assignable agenda (`AgendaService.assignable`/`add_in_tx`), the vote create check (`VotingService._application_gremium_id`), the task mail (`actionable_principal_emails`) and the guard `isInVoteGremium`. A target with `gremiumSource: "budget"` and no resolvable Gremium: the list hides the transition, a manual fire / force / audit revert gives 409 `no_vote_gremium`, `auto_advance` skips it, a vote branch is blocked (`vote_branch_blocked`, reason `no_vote_gremium`). The flow activation re-derives the snapshot (`FlowOps._move_vote_gremium`). `POST /applications/{id}/assign-budget` gives 409 `budget_locked_by_vote` while the application sits in a `gremiumSource: "budget"` vote state, and the `assignBudget*` actions skip there.
- Strongly-typed Python ≥3.13 (see the `conventions` skill). All errors are `ProblemDetail` (RFC-9457). Revert scope: [[revert-feature-scope]].
