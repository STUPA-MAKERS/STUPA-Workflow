# Flow / Status Engine — `backend/app/modules/flow`

**Does:** Runs the global declarative state machine that every application moves through. It evaluates guards, fires transitions atomically with audit, deadline and worker actions, and lists the firable transitions for a principal. The admin module stores and edits the graph itself (states and transitions). This module is the runtime engine.

**Key files:**
- `service.py` — `FlowService`: `available_transitions`, `fire`, `auto_advance`, `fire_branch`/`branch_transition`, `available_applicant_transitions`/`fire_as_applicant`, `schedule_state_deadline`, `revert_status`. The CRITICAL core.
- `context.py` — `build_context()`: assembles the pure `GuardContext` from the DB (actor Gremien, applicant roles and Gremien, budget fit, field values and types).
- `dispatch.py` — `DispatchedAction`, `build_dispatched_actions` (worker whitelist filter), `build_implicit_notifications` (auto applicant + task mail), `ActionDispatcher` protocol, `NullActionDispatcher` (log-only default), `ChainActionDispatcher`, `build_worker_dispatcher(redis, sessionmaker, settings)` (the full chain: notify, webhook, extras).
- `extras_dispatcher.py` — `FlowExtrasActionDispatcher`: in-process handlers for `addToNextSession`, `assignBudget` and `assignBudgetFromField`. The budget assignment is idempotent: a retry that finds the cost center set changes nothing and writes no second audit entry.
- `router.py` — the application-transition routes. `MANAGE_PERMISSION = "application.transition"`. `get_action_dispatcher` is THE dispatcher dependency: `app.main` overrides it with `build_worker_dispatcher`, and the voting and live-vote routers depend on it too. Never add a second local dispatcher dependency: the override would not reach it (F2).
- `models.py` — `FlowVersion`, `State`, `Transition` tables.
- `schemas.py` — `TransitionOut` (with `addsToAgenda`, `agendaGremiumId`), `TransitionRequest` (with optional `meetingId`, `nonPublic`), `TransitionResult` (camelCase aliases).
- `../../shared/guards.py` — the pure guard evaluator + whitelists + `validate_guard`/`validate_action` (lives in `app/shared`, not in this module).
- `../../shared/config_schemas.py` — `FlowGraph` + `validate_flow_graph` (the graph save-gate and validator).

**Domain / data model:**
- `flow_version` — the ONE global flow (typed flows removed, migration 0019). Partial-unique `uq_flow_version_one_active_global` → exactly one `active` row. Cols: `version` (unique), `active`, `editor_layout` (JSONB).
- `state` — `flow_version_id` (FK CASCADE), `key`, `label_i18n`, `color`, `edit_allowed`, `is_initial`, `is_terminal`, `kind`, `config` (JSONB). `kind ∈ {normal, vote}` (CHECK `state_kind`, approval and decision removed). One partial-unique `is_initial` per flow. Unique `(flow_version_id, key)`. `config.deadlinePolicyKey` materializes a deadline on entry. A `vote` state needs `config.gremiumId`.
- `transition` — `flow_version_id`, `from_state_id`, `to_state_id` (all FK CASCADE), `label_i18n`, `color`, `guard` (JSONB | NULL), `actions` (JSONB list), `order`, `automatic` (the worker fires it when the guard is true), `branch` (`pass`/`fail` for vote-state exits, else NULL), `requires_action` (counts as an open task). The edit lock derives from the target `state.edit_allowed`. `applications.patch` handles it inline and returns 409. It is NOT a dispatched action.
- A fired transition writes a `StatusEvent` (in `applications.models`) + a `status_change` audit entry in the same transaction.

**Guard catalog (`shared/guards.py`):** declarative, whitelist, NO eval. `eval_guard(guard, ctx)` takes a single-key dict. An empty guard or None gives True.
- Combinators: `and`, `or`, `not`.
- Conditions (auto + manual): `deadlinePassed`, `applicantRoleIs`, `applicantCommitteeIs`, `budgetIs`, `budgetFitsApplication`, `hasField`, `compare` ({field, op, value}, typed by the field type of the pinned form version, fail-closed on a missing field or an unknown op).
- Actor gates (MANUAL only, rejected on automatic transitions by `allow_actor_ops=False`): `roleIs`, `isInCommittee`, `actorIsApplicant`.
- Action whitelist: `webhook` (needs `webhookId`), `notify` (needs `recipients[]` of kind gremium/role/applicant/email), `addToNextSession` (needs `gremiumId`, only on a transition INTO a vote state), `assignBudget` (needs `budgetId`), `assignBudgetFromField` (needs `field`, the form field that holds the cost center id). An unknown operator or action raises `GuardError` at SAVE time (`validate_guard`/`validate_action`/`validate_flow_graph`), not at runtime.

**API surface:**
- `GET  /api/applications/{id}/transitions` — P(`application.transition`). The firable manual transitions. The engine evaluates the guards for the principal and excludes `automatic` and `branch`. `addsToAgenda`/`agendaGremiumId` flag a transition with `addToNextSession` (the "put on the agenda" dialog).
- `POST /api/applications/{id}/transition` — P(`application.transition`). Fire a transition → 200 `{newStateId, statusEventId, dispatchedActions}` or 409 on a guard, a state conflict or a race. Optional `meetingId` + `nonPublic` (A1): before the state change the engine checks that the transition has `addToNextSession`, its target is a vote state, and the meeting is readable, `planned` and of the action Gremium, else 422 `agenda_meeting_invalid`. `AgendaService.add_in_tx` then adds the item in the same transaction (a refusal rolls everything back, 422), and the post-commit `addToNextSession` is skipped.
- `GET  /api/applications/{id}/applicant-transitions` — magic-link applicant. Only manual transitions gated by `actorIsApplicant`.
- `POST /api/applications/{id}/applicant-transition` — fire as applicant (403 unless `actorIsApplicant` opened it).
- Flow GRAPH CRUD is NOT here. It lives in the admin module: `GET/POST /api/flow-versions/global` (`AdminService.get_active_global_flow`/`create_global_flow_version`), validated by `validate_flow_graph`.

**Conventions & gotchas:**
- `fire()` uses optimistic locking. The rowcount of `UPDATE … WHERE current_state_id = from_state_id` must be 1, else the call gives 409 for a concurrent transition. Always re-check the state, never assume it.
- Only the vote outcome fires a branch transition (`pass`/`fail`) with `manual=False`. A manual `fire` of a branch transition gives 409, because nobody may set a vote result by hand. The vote close calls `stage_branch` inside a SAVEPOINT (`session.begin_nested()`) and commits the close and the transition ONCE (F20). On a guard failure, a lost race or a missing branch only the SAVEPOINT rolls back, so `stage_fire` takes `rollback_on_conflict=False` there. `fire_branch` (commit included) stays for direct callers.
- `fire` = `stage_fire` (all writes, no commit, returns a `StagedFire`) + commit + `after_commit` (deadline of the new state, `vote_cancelled` events, worker actions). `schedule_staged_deadline(staged, commit=False)` lets the vote close commit the deadline in the same transaction.
- **Leaving a vote state cancels its votes (F19, F22).** A transition without a branch, `force_status` and `revert_status` call `VotingService.cancel_for_application`: every `open` vote of the application and the drafts of the state that the application leaves become `cancelled`, get `closed_at` and a `vote_cancel` audit entry (reason `state_left`). A draft belongs to the left state when its `opens_state_id` is that state, or when `opens_state_id` is NULL and the left state is a vote state (`kind == 'vote'` or a `pass`/`fail` exit). Every other draft stays: a draft without `opens_state_id` survives the transition INTO the vote state, and a draft for a later vote state survives too. A transition back into the same state keeps every draft. After the commit `_publish_cancelled` sends `vote_cancelled` through the optional `MeetingPublisher` (`FlowService(session, dispatcher, publisher)`; the flow router, the audit revert route and the worker pass one). A broker fault only logs. A vote branch cancels nothing, because the close owns the vote.
- `auto_advance` NEVER fires out of a `vote` state. This is fail-closed, and the validator also forbids an automatic non-branch exit from a vote state. Otherwise the engine would approve an application without a vote.
- The engine fills the actor roles and Gremien only for a `manual=True` context. An automatic run sees empty actor sets, so an actor gate cannot pass.
- Worker actions dispatch AFTER the commit. They are idempotent and retryable and carry a stable `idempotency_key`. The engine logs an action failure and swallows it. An action must never roll back the committed state change. `build_dispatched_actions` filters again to the worker whitelist (`notify`, `webhook`, `addToNextSession`, `assignBudget`, `assignBudgetFromField`). It skips `setEditLock` and the rest. Keep `WORKER_ACTION_TYPES` in sync with the validator whitelist: an action missing there never runs (F1).
- Every path that fires runs the full chain: the manual route, `POST /votes/{id}/close`, the live-vote routes (app override) and the worker (`ctx["flow_dispatcher"]`, set in `worker.main._on_startup`).
- `addToNextSession` after the commit takes the earliest meeting of the Gremium with `status = planned` and `date >= today` in `settings.local_timezone`. A live or closed meeting never gets the item. Without such a meeting it only logs (F3).
- The guard `attachmentPresent` counts only attachments with `scanned = true`, `scan_result = 'clean'` and a `storage_key` (F13).
- Every fire emits implicit mails: a `notify` to the applicant and a `taskNotify` to the actors of the new state. An explicit applicant `notify` in the config replaces the implicit one.
- Deadlines: on entry into a state, `schedule_state_deadline(app, state, *, commit=True, due_at=None)` deletes the `flow_deadline` rows of the state you leave and returns the new row. If `config.deadlinePolicyKey` resolves, it creates a new row. That row pins the `order`-first transition whose guard fires on the elapsed deadline alone (`_DEADLINE_ONLY_CTX`). The T-44 cron fires it. On a manual path the engine reads `deadlinePassed` from the DB. A new flow version re-creates the deadlines of the moved applications (`commit=False`, F6). With the same policy key it passes the old `due_at`, so a passed `recurring` date stays passed, and a PATCH re-creates a `relative_changed` deadline (F7).
- `revert_status` (audit-log revert) flips the state back ONLY while the application still sits in `to_state_id`, else 409 `stale_revert`. It re-materializes the deadline and cancels the votes of the state it leaves (F22, see above). It does NOT undo other side effects: a cancelled vote stays cancelled, and sent webhooks and mails stay sent. `config_revision.revert` calls it (`RevertService(session, publisher)`).
- Strongly-typed Python ≥3.13 ([[python-strong-typing]]). All errors are `ProblemDetail` (RFC-9457). See the `conventions` skill. Revert scope: [[revert-feature-scope]]. Flow redesign spec: [[flow-engine-redesign]]. Prior fixes: [[flow-engine-bug-fixes]].
