# Live-Vote / Meetings — `backend/app/modules/livevote`

**Does:** Manages Gremium meetings: CRUD plus lifecycle control, agenda items, and attendance. It also runs a Redis pub/sub live-vote channel with a voter WebSocket (cast/subscribe) and a read-only beamer stream. This is the second-largest backend module. The service creates the protocol lazily when a meeting goes live.

**Key files:**
- `models.py` — `Meeting`, `MeetingAttendance`, `MeetingAgendaItem`, `ProtocolKeeperPeriod` ORM tables.
- `keepers.py` — read helpers of the protocol keeper: `keeper_principal_ids` (members with `protocol.write`, O20), `agenda_positions`, `keeper_periods`, `keeper_summaries` (the A13 fields of `MeetingOut`).
- `service/handover.py` — `HandoverOps` (mixed into `MeetingService`): the keeper periods (Z3), `hand_over`, `cancel_handover`, and the hooks that `lifecycle.patch` calls (`open_first_period`, `activate_planned`, `switch_now`, `close_periods`, `check_keeper`).
- `schemas.py` — Pydantic API I/O (`MeetingCreate/Patch/Out`, `MeetingVoteOut`, `MeetingPage`, agenda + attendance bodies) with camelCase aliases and `populate_by_name`.
- `events.py` — WS message contract (single source): server→client `meeting_state|vote_opened|vote_tally|vote_closed|vote_cancelled|viewers|error`, client→server `cast|subscribe`. `VoteTallyEvent.from_vote` enforces the "counts only at close" secrecy rule. The `vote_opened` of the state on a connect or `subscribe` carries `replay: true` (a broadcast carries `false`), so a client can tell an open vote from a vote that opens now.
- `router.py` — REST routes plus the two WS endpoints. It holds the per-(meeting,principal) connection cap and the field-level RBAC gating. On `planned→live` it creates the protocol.
- `service.py` — `MeetingService` (lifecycle, timeline, RBAC, vote decoration) plus `BrokerPublisher`. `BrokerPublisher` builds WS events from voting schemas and implements the leaf `MeetingPublisher` protocol, so `voting` does not import `livevote`. `meeting_channel(id)` → `meeting:{id}`.
- `agenda_service.py` — `AgendaService`: assign/remove/reorder agenda items, with the state rules (F24, O22, O25) and the agenda audit (F12). "assignable" = applications whose current state is a `vote` state with `config.gremiumId` == meeting gremium. `agenda_order()` is the one sort order (position, created_at, id) for the agenda list and the `MeetingOut` summary.
- `attendance_service.py` — `AttendanceService`: roster of the meeting (see `roster.py`), the own report, the lead's set and reset, with the attendance rules (Z2, O15, O23) and the attendance audit (F12).
- `roster.py` — the roster of one meeting: `meeting_window` (start = `started_at`, else the planned start; end = `closed_at` for a closed meeting, else now; a future planned meeting gets "now") and `meeting_roster_filter` = members whose term overlaps the window UNION every principal with a `meeting_attendance` row, as one `IN … OR IN …` clause on `principal.id`. `planned_start_utc` is the one planned-start helper (`delegations.service.meeting_start_utc` calls it).
- `connection.py` — `LiveVoteConnection` WS handler: handshake auth (`resolve_ws_principal`), Origin/CSWSH check, token-bucket throttle, cast (distributed lock → `VotingService.cast`), broker fan-out pump, presence.
- `broker.py` — `MeetingBroker` protocol with `RedisBroker` (prod) and `InMemoryBroker` (tests/single-proc).
- `locks.py` — `Locker` protocol. `RedisLocker` (`SET NX PX` + Lua CAS release) or `InMemoryLocker`, key `vote:{id}:cast:{sub}`.
- `presence.py` — in-memory `PRESENCE` register of open voter connections (`viewers` event), single-replica scope.
- `publisher.py` — `MeetingPublisher` protocol + `NullPublisher` default (injected from app state in `create_app`).

**Domain / data model:**
- `meeting`: `gremium_id`(FK CASCADE), `title`, `date`, `start_time`/`end_time`, `status` IN `planned|live|closed` (CHECK, `closed` is terminal), `started_at` (Z7/O9: set once on `planned→live`. Migration `eff772f93d8e` adds it without a backfill, because the audit log holds no meeting start. An older live or closed meeting keeps NULL, and a reader shows the planned start.), `closed_at` (set once on close), `active_application_id`(FK SET NULL — beamer focus), `protokollant_id`(FK principal SET NULL — exactly one, required before going live), `created_by`.
- `protocol_keeper_period` (Z3, migration `734556b61a72`): one period in which one principal keeps the minutes. `meeting_id` CASCADE, `principal_id` NO ACTION (principal rows are never deleted), `from_at` (NULL = planned), `to_at` (NULL = running), `from_agenda_item_id`/`to_agenda_item_id` SET NULL, `handed_over_by` (the actor `sub`, `system:migration` for the backfill). Check `ck_protocol_keeper_period_period_range`: `to_at IS NULL OR (from_at IS NOT NULL AND to_at >= from_at)`. Partial unique indexes: at most one running (`uq_protocol_keeper_period_running`) and one planned (`uq_protocol_keeper_period_planned`) period per meeting. The backfill gives each live or closed meeting with a protokollant one period: from `started_at`, else the planned start in Europe/Berlin, else `created_at`; a closed one ends at `GREATEST(COALESCE(closed_at, from_at), from_at)`.
- `meeting_attendance`: one row per `(meeting_id, principal_id)` (UNIQUE upsert). Columns: `status` IN `present|excused|absent`, `source` IN `self|lead`, `note` (the reason of an excuse, personal data, max. 500 characters). Check `ck_meeting_attendance_self_status` (Z2): `source <> 'self' OR status IN ('present','excused')`. Migration `96421ecdbc54` adds it `NOT VALID`, so an older `(self, absent)` row stays, but every new or changed row must pass. A change to such an older row must set an allowed status. That is why the principal erasure clears `note` only `WHERE note IS NOT NULL`.
- `meeting_agenda_item`: agenda item = assigned `application_id` (nullable, NULL means a free-text agenda item that uses `title`), `body` (Markdown per agenda item, feeds the final protocol), `position` (ordered), `non_public` (redacted in public protocol PDF, numbering preserved). UNIQUE `(meeting_id, application_id)`.
- This module does not store votes. They live in `voting` (`Vote.meeting_id`/`agenda_item_id`). The service decorates `MeetingOut.votes` with `MeetingVoteOut` (counts/leading/voted/present/revealed/failedReason, plus A5: `majorityRule`, `secret`, `quorum`, `openedAt`, `closedAt`, `myBallot` and `representedCast`). `_votes_for(meeting_ids, principal)` fills `myBallot`/`representedCast` for the caller with three batched queries (`_ballots_of`: the voting delegations of the caller in these meetings, the own and the delegator ballots, the voted markers). A secret vote gives only `myBallot.cast`. Without a principal (a broadcast) `myBallot` is None.
- A13: `MeetingOut.keeperPeriods` (the running and ended periods in time order: principal, name, `fromAt`/`toAt`, agenda item ids and their 1-based positions) and `plannedHandover`. Detail and list fill them in batches (`keeper_summaries`).
- `MeetingOut` carries computed RBAC flags: `canControl/canManage/canWrite/canManageVotes/canVote`, `isProtokollant`, plus `protocolId`, `gremiumName`, `protokollantName`, `startedAt`, `closedAt`. A2: `agendaItemCount` and `currentAgendaItem {position, title}` (the 1-based number in agenda order, and the title of the free-text item or of the application). `MeetingServiceBase._agenda_summaries` builds both with two batched queries for the detail (`PermissionOps._emit`) and the list (`ListingOps._decorate`).

**API surface:**
- `POST /api/meetings` — create (planned). Sends a meeting mail as a background task.
- `GET /api/meetings` / `GET /api/meetings/timeline` — list / keyset-paginated timeline (`direction=past|upcoming`, opaque `cursor`, fuzzy `q` collapses to one ranked list with offset cursor). The list takes `gremiumId` and the optional `dateFrom`/`dateTo` (`YYYY-MM-DD`, both included; the calendar view reads one month this way; a meeting without a date is then not in the list; `dateFrom` after `dateTo` gives 422 `invalid_date_range`). Every list shape carries `agendaItemCount` ("n TOPs" of the overview).
- `GET /api/meetings/gremien` — gremien filter (visibility-based, must precede `{meeting_id}`).
- `GET /api/meetings/{id}` — state. `PATCH /api/meetings/{id}` — control and planning, broadcasts `meeting_state`. `title` (same rule as the create: stripped, 1 to 200 characters, `null` gives 422) needs `canManage` and changes only while the meeting is `planned` or `live`. A closed meeting keeps its title (409), because the protocol that goes out names the meeting. 409 `invalid_status_transition` and 409 `open_vote` (see the lifecycle invariants). `DELETE` — manager only, 409 `open_vote` while a vote of the meeting is open. This is also how a planned meeting that does not take place goes away.
- `GET /api/gremien/{gremium_id}/meeting-members` — protokollant candidates. `canKeepProtocol` marks the members with `protocol.write` (O20). The roster (`AttendanceOut`) carries the same flag, so the keeper of a live meeting, who may lack `session.manage`, gets the candidates too.
- `POST /api/meetings/{id}/protokollant-handover` `{principalId, mode: now|next_item}` (Z3, O1) — only while `live` (409 `meeting_not_live`). Callers: `can_manage` or the current protokollant (scope-capped by `protocol.write`), else 403. The target is an active member (403) with `protocol.write` (O20: 422 `protokollant_needs_protocol_write`); the current keeper gives 409 `already_protokollant`. `now` ends the running period at the current agenda item and opens the next one, and a planned handover goes away. `next_item` plans the period (it replaces an older plan); the last agenda item, or an empty agenda, gives 409 `no_next_item`. `DELETE` on the same path discards the plan (404 `no_planned_handover`). Each call locks the meeting row, writes `protokollant_handover` (`mode` now/next_item/cancel) and sends `meeting_state`.
- `GET .../attendance` — roster of the meeting, never "members valid now" for a past meeting. A recorded attendance never drops out: the OIDC sync deletes the membership rows of a principal who leaves a mapped group (and migration `097f61e33e3c` of #240 deleted all older memberships), so a closed meeting must not depend on `gremium_membership` of today. A member whose membership starts after the window is not on it. `canKeepProtocol` still reflects the keepers of now, and `canVote` the members with the gremium permission `vote.cast` now (one query, `keepers.member_permissions`; the O6 lead entry is offered only for them). The writes (`attendance/me`, lead set) still need a membership that is valid now. `AttendanceOut` carries `status`, `source` (`self|lead`, `null` = open), `note` and `isSelf`. A7: `note` goes only to the member (`isSelf`) and to the meeting lead (`canWrite`), all other readers get `null`.
- `PUT .../attendance/me` — the own report (Z2): `AttendanceSelfBody.status` is `present|excused` only (`absent` gives 422), in `planned` and `live`. O15: a record with `source='lead'` gives 409 `attendance_set_by_lead`. O23: `present` gives 409 `delegation_active` while the member has a delegation for the meeting, as on the lead path. That includes a substitution that the lead entered during the live meeting (O6). The share lock on the meeting row (`_meeting(for_write=True)`) is what keeps this check safe: the lead entry takes the same row `FOR UPDATE`, so the two run one after the other. Do not drop the lock. Not audited.
- `PUT .../attendance/{principal_id}` — the lead (`canWrite`) sets any status, `source='lead'`. O23: `present` gives 409 `delegation_active` while a `MeetingDelegation` with this delegator exists for the meeting. The delegation must be revoked first: the delegator can revoke it only before the meeting start, the meeting lead (`can_manage`) while the meeting is live (O6, also for a substitution the lead entered), an admin always (`DelegationService.revoke`). Writes `attendance_set`. A lead set always takes the record over (`source='lead'`), so the session page shows the reason input to the lead only on a lead row or on the own row; the reason of a member's own excuse is read-only for the lead.
- `DELETE .../attendance/{principal_id}` — the lead resets the member to "open": the record goes away, so the member can report again. Writes `attendance_reset`. No record = no change, no audit.
- The attendance bodies take an optional `note`, allowed only with `excused` (else 422). An omitted `note` keeps the stored reason while the status stays `excused`, an explicit `null` or empty text removes it, and any other status removes it. All attendance writes give 409 on a `closed` meeting and take a share lock on the meeting row first (a close holds it for update), then a row lock on the record. When no record exists, there is nothing to lock: a parallel first self report and lead set both insert, and the unique constraint refuses the second one. The service maps that `IntegrityError` to 409 `conflict`.
- `GET .../agenda`, `GET .../agenda/assignable`, `POST .../agenda`, `DELETE .../agenda/{item_id}`, `PUT .../agenda/order`, `PATCH .../agenda/{item_id}` (body/title/nonPublic). All writes need `canWrite`. State rules (F24, O25): add, rename, reorder and remove need `planned` or `live` (409 `meeting_closed`). Remove gives 409 `agenda_item_has_vote` while the item has an `open` or `closed` vote. It deletes the `draft` and `cancelled` votes of the item first, each with `vote_delete` (`VotingService.delete_for_agenda_item`). To delete these votes the caller also needs `canManageVotes` (the gate of the vote delete route), else 403: `protocol.write` alone removes only an item without votes. O22: `body` needs `live`, or `closed` while the protocol is `draft` (409 `meeting_not_started` / `protocol_locked`). `nonPublic` is open from `planned` until the protocol leaves `draft`.
- `POST .../votes` — create and open the decision vote of an agenda item. It builds a `VoteCreateInternal` (gremium of the meeting, `eligibleCount` from `vote_eligible_count`) and calls `VotingService.create_internal`. An application agenda item allows exactly one vote, a free-text agenda item allows many. The route stores `tieBreak=rejected` (O18): a meeting vote has no casting vote, so a tie is `rejected`. `MeetingVoteOpenBody` has no `tieBreak`. The open writes `vote_open` with the caller as the actor. `DELETE .../votes/{vote_id}` — delete a vote (`canManageVotes`). O24: only in a `planned` or `live` meeting (409 `meeting_closed` after the close). Only a `draft` or `cancelled` vote: an `open` or `closed` vote gives 409 `vote_not_deletable` (cancel an open vote first), so the O25 rule for the agenda item holds. Every delete writes `vote_delete`.
- `WS /api/ws/meetings/{id}` — voter channel (cast/subscribe). `WS /api/ws/meetings/{id}/beamer` — read-only, carries only `meeting_state|vote_opened|vote_tally|vote_closed`.

**Conventions & gotchas:**
- The server resolves RBAC from the session and scopes it per Gremium, never from the body (see [[admin-domain-rules]], [[sessions-protokollant-redesign]]). `canManage` = admin OR per-Gremium `session.manage` (no global key since `3a0b9672fcba`). `canWrite` (status, agenda items, protocol) adds the assigned protokollant OR a role with `protocol.write`. `canManageVotes` adds `vote.manage`. `canFinalize` = `canWrite` AND (admin OR per-Gremium `protocol.finalize`). `canVote` = `vote.cast` in the Gremium OR a voting delegation for this meeting. PATCH is field-gated: date, time and protokollant need `canManage`, status and activeApplication need `canWrite`.
- **Scope cap (F16):** every flag goes through `gremium_ids_for` / `admin_bypass` (`admin/gremium_roles.py`), and the protokollant path checks `principal.scope_allows(...)` too. A `read` token can therefore not manage, write or run votes. `_visible_gremium_ids` returns `None` (all Gremien) for `meeting.view_all` (part of the `read` scope) or the admin bypass of `session.manage`; else the member gremien plus the pool gremien from `delegations.pool.substitute_gremien_for_sub` (the `delegation_substitute` entries). The batched list flags in `listing._decorate` mirror the detail flags in `PermissionOps`; change both together.
- The beamer WS needs `can_manage(meeting.gremium_id)`, that is `session.manage` in the Gremium of the meeting or admin. The frontend route uses `gremiumPermission: 'session.manage'`.
- **Keeper periods (Z3):** `meeting.protokollant_id` always names the keeper of the running period. The start opens the first period. A forward move of `current_agenda_item_id` (the new item comes later in `agenda_order()`, or no item was current) starts the planned period in the same transaction: the old period ends at the old item, `protokollant_id` changes, and `protokollant_handover` (`mode=activate`) is written. A move back keeps the plan. `PATCH protokollantId` on a live meeting is a handover `now` (`null` gives 409); the same value again is a no-op, so the settings dialog can send it with each save. The close ends the running period at `closed_at` and drops the planned one. A handover moves the rights that follow the keeper: `can_write` and `can_manage_votes`. A member with `protocol.write` keeps the write access after the handover; only the room control moves. A handover never writes `protokollantId` into `meeting_update`. O20: a new assignment (create, PATCH) needs `protocol.write` (422); an already assigned keeper without it can still start the meeting. `patch` locks the meeting row for a status change, a move of the agenda item and a protokollant change.
- **Lifecycle invariants (F9, O13):** the status runs only `planned→live→closed` (`lifecycle._TRANSITIONS`). A repeat of the current status is a no-op. Every other change (live→planned, planned→closed, closed→anything) gives 409 `invalid_status_transition`. A meeting that does not take place is deleted, not closed. `planned→live` requires a protokollant, else 409, and sets `started_at` once. Only this transition creates the protocol, and the create is idempotent. It uses a local import of `ProtocolService` to avoid an import cycle. The API rejects votes and agenda item `body` edits before `live`. **Close (O12):** `live→closed` gives 409 `open_vote` while a vote of the meeting is `open`. Otherwise it sets `closed_at`, cancels the `draft` votes of the meeting in the same transaction (`VotingService.cancel_drafts_for_meeting`, audit `vote_cancel` reason `meeting_closed`) and publishes `vote_cancelled` after the commit (best effort, a broker fault only logs). `closed` is terminal and freezes date, time and protokollant. The protokollant cannot change after the protocol is final. **Meeting row lock:** a status change (`patch` with `status`), the meeting delete, the agenda add (`add_in_tx`) and remove, and the vote create and open of a meeting vote (`VotingService._lock_live_meeting`) all take `SELECT … FOR UPDATE` on the `meeting` row first. Thus a vote cannot open while the meeting closes, and it cannot bind to an item that is removed at the same time. Lock order: meeting row first, vote rows after it. Do not lock a vote row and then the meeting.
- **Audit (F12):** `meeting_create` (gremium and planning values), `meeting_update` (a status or planning change as `{"from", "to"}` per field, without the current agenda item and the beamer focus), `meeting_delete` (with `deletedVotes` and `deletedVoteIds`), `agenda_item_add`, `agenda_item_update` (changed field names only, never the Markdown. A body edit counts only after the close, as a correction of the minutes. The live autosave writes no entry.), `agenda_item_remove` (with the deleted vote ids) and `agenda_reorder` (the new id order), `attendance_set` and `attendance_reset` (the principal id, `status` and `source` as `{"from", "to"}`, never the note; the own report of a member writes no entry). The flow action `addToNextSession` adds its item with the firing principal as the actor.
- **Meeting delete deletes the votes (user decision 2026-10-06, replaces F21):** the delete locks the meeting row, gives 409 `open_vote` while a vote is `open`, and checks `meeting.delete_finalized` for a final protocol. Then, in the same transaction, `VotingService.delete_for_meeting` locks and deletes EVERY vote of the meeting (draft, cancelled, closed, secret, with guests). It deletes in this order: `protocol_vote_ref`, `secret_ballot`, `voted_marker`, `ballot` (the guest ballots too), then it sets `status_event.vote_id` to NULL and deletes each vote with `vote_delete` (reason `meeting_deleted`, id references and status only). `meeting_delete` carries `deletedVotes` (count) and `deletedVoteIds`, never a choice or a name. The delete sends no `vote_cancelled`. An application that such a vote decided keeps its status; its timeline shows "Abstimmung gelöscht (mit Sitzung)" (see `be-applications`). The FKs `vote.meeting_id` and `vote.agenda_item_id` stay `ON DELETE SET NULL` for a delete outside the service (a gremium delete cascades to its meetings, and its votes then detach). The delete dialog loads the meeting and names the number of its votes.
- **Vote secrecy / aggregate-only:** beamer and tally events carry only aggregates, never voter identities. While a `secret` vote is open, the tally hides `counts`/`leading` and shows only the participation `cast/eligible`. `VoteTallyEvent.from_vote` is the single enforcement point. Always build tallies through it.
- Votes on an application agenda item fail fast. The application must be in a `vote` state that matches `config.gremiumId` before the vote opens. Otherwise voters waste ballots on a vote that cannot close.
- **WS security:** the handshake authenticates from the session cookie. The CSRF middleware does NOT run on upgrades, so an explicit `Origin` allowlist guards against CSWSH. Close codes: `4401` (no session), `4403` (not eligible, after a `not_eligible` error frame), `4404`. A per-(meeting,sub) connection cap (`_MAX_CONNECTIONS_PER_PRINCIPAL=5`) and a per-connection token-bucket throttle (`rate_limited`) apply.
- The distributed lock `vote:{id}:cast:{sub}` serializes casting per voter (`:proxy` suffix for delegation casts). The real guarantee is the DB UNIQUE on `(vote_id, voter)`, so the lock is defense in depth. An own cast and a delegation cast are two separate casts (`asDelegation`). A ballot never changes after the cast (O11): a second cast gets the error frame `already_voted`, the same code as the REST 409.
- Presence (`viewers`) and the connection cap live in memory per process. That is a documented single-replica limit. Only the broker (Redis) fans out across instances.
- The broker and the locker come from `app.state`, with in-memory fallbacks for tests. Both are `Protocol`s, so you override them via `dependency_overrides`.

**Public meeting with a QR code (#17):**
- Data: `meeting.public_join` (bool), `meeting.guests_mode` (`vote|watch`, CHECK `ck_meeting_guests_mode`), `meeting.join_code` (6 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`; partial unique index `uq_meeting_join_code_open` among the meetings that are not closed). Table `meeting_guest` (`guests.py`, model `MeetingGuest`): `seq` (the pseudonym number "Gast n"), `display_name` (NULL after the pseudonymization), `status` `pending|admitted|rejected|removed|left`, `token_hash` (SHA-256 of the device token, never the token), `requested_at`, `decided_at`, `decided_by` (FK principal, SET NULL; listed in the account merge), `admitted_at` (set = took part), `last_seen_at`. Migration `4c2570138998`.
- `MeetingOut` carries `publicJoin`, `guestsMode`, `admittedGuests`, and for `canManage` only `joinCode` and `pendingGuests`. `MeetingCreate`/`MeetingPatch` take `publicJoin`/`guestsMode` (`canManage`). The first switch-on creates the code. `lifecycle._apply_public`: `vote`→`watch` gives 409 `guest_vote_open` while a vote with guests is open; switch-off deletes the open requests and sets the admitted guests to `removed` (cast ballots stay); a change writes `meeting_public_join_changed`. The close deletes every row without `admitted_at` and every token hash (`GuestService.purge_on_close`).
- Lead routes (`session.manage` in the gremium, `_require_manage`): `GET /meetings/{id}/guests`, `POST …/guests/{gid}/admit|reject|remove|rename`, `POST …/guests/admit-all`, `GET …/join-link` (code, absolute URL from `PUBLIC_BASE_URL`, QR matrix from `segno`), `POST …/join-code/rotate` (voids the open requests; the admitted guests keep their token). Audit: `guest_admitted`, `guest_rejected`, `guest_removed`, `guest_renamed`, `guest_admit_all` (count + ids), `meeting_join_code_rotated` — ids and counts only, never a name or a code.
- Public routes (`public_router.py`, prefix `/api/public/meetings`, no session): `GET /{code}` (head), `POST /join/{code}` (ALTCHA, body cap, `rate_limit_public_join` per IP and per code; sets the cookie `mg_token` HttpOnly, SameSite=Strict, path `/api/public/meetings`), `GET|PATCH|DELETE /{code}/me`, `POST /{code}/votes/{voteId}/ballot`. One device = one token; a second request replaces the first; a rejected or removed device waits 3 minutes (429 `retry_later` + `Retry-After`). `resolve` accepts a stale code only for an admitted guest (rotation). The default write limit per IP skips this prefix (`middleware.PUBLIC_MEETING_PREFIX`); the CSRF double submit covers the `mg_token` cookie.
- Guest view (`GuestMe.view`, admitted only): agenda in `agenda_order()` with titles also of non-public items, `body` only of public items; the open and closed votes of public items with tally, `myBallot`, `canCast`. Never other names, attendance or delegations.
- WebSockets: `/api/public/meetings/{code}/ws` (`guest_connection.py`, cookie auth, Origin check, 3 sockets per guest): `guest_status` (own state), then for an admitted guest `meeting_state` (status and item only), the vote events of public items, `guest_counts` (`admittedGuests`). The member channel filters `guest_requested`/`guest_updated` to `canManage` connections and strips `joinCode`/`pendingGuests` from `guest_counts` for the others; the beamer gets `guest_counts`.
- Review rulings and limits: public participation is allowed only in a gremium without a quorum (`gremium.quorum_percent IS NULL`; 422 `public_join_needs_no_quorum` on create and on the switch-on; `MeetingOut.publicJoinAllowed`, `GET /gremien/{id}/meeting-defaults`). The close pseudonymizes all guests at once (names NULL, numbers stay) and sends `guest_updated` (`expired`, reason `meeting_closed`) for the deleted rows; a waiting device socket closes with the meeting. A device that joins another meeting leaves the first one (`left`, name gone, `guest_updated` there). Unknown code, closed meeting and switched-off meeting answer the same 404 `join_code_unknown` on the head and the join. The guest writes count per resolved guest, else per IP (random cookies share the IP budget); the guest socket handshake counts per IP (close 4429). The join code assignment retries in a SAVEPOINT on a unique collision. The cookie lives until the end of the day after the meeting day (at least 24 h). Known limits: the 3-minute wait after a rejection binds only a device that keeps its cookie (a private window or a cleared cookie gets around it; then only ALTCHA and the limits per IP and per code apply). A member can also join as a guest from a second browser; only the admission by the lead prevents a double vote. The beamer needs `session.manage`, so only the lead opens it (with the QR).
- Votes with guests: `MeetingVoteOpenBody.guestsVote` (default on in a meeting where guests vote and on a public item; 422 `guests_vote_unavailable` / `guests_vote_non_public`). Such a vote has no quorum; `eligible_count` = present members + admitted guests (fixed again at the close). `MeetingVoteOut` adds `guestsVote`, `presentMembers`, `presentGuests`; `present` includes the admitted guests. `nonPublic=true` on an item with such a vote gives 409 `guests_vote_on_item`.
